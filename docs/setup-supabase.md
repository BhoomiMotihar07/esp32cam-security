# Supabase + Render setup (works from anywhere, free)

An alternative to the Azure deployment. Same app, API code and firmware; only three backend
adapters change (`APP_MODE=supabase`).

| piece | Azure version | Supabase version |
|---|---|---|
| database | Cosmos DB | Supabase Postgres (JSONB document tables) |
| photos | Blob Storage + SAS | Supabase Storage private bucket + signed URLs |
| device → cloud | IoT Hub MQTT | HTTPS `POST /api/device/{id}/telemetry` with `x-device-key` |
| cloud → device | IoT Hub C2D | `device_commands` table, polled by `GET /api/device/{id}/commands` every 3 s |
| API, timers | Azure Functions | the Node server on Render's free plan |
| app hosting | Static Web Apps | the same Render service (one URL for app + API) |

> The course spec names Azure IoT Hub. Check with your instructor before submitting this variant.

## 1. Supabase project

1. supabase.com → New project (free plan, region `ap-south-1` Mumbai). Save the database password.
2. SQL Editor → paste and run [`api/supabase/schema.sql`](../api/supabase/schema.sql). It creates
   five tables with row-level security on and **no policies** (only the server's service-role key
   can touch them) and a private `evidence` bucket (JPEG only, 2 MB max).
3. Project Settings → API: copy the **Project URL** and the **service_role** secret key.
   The service-role key bypasses RLS: it goes only into Render's environment, never into the app,
   the firmware or git.

Free-plan limits that matter: 500 MB database, 1 GB storage (≈ 25,000 evidence photos at 40 KB),
and projects are **paused after 7 days without activity**. A running camera sends a heartbeat
every minute, so an active system stays awake.

## 2. Render web service

The repo has a [`render.yaml`](../render.yaml) blueprint.

1. render.com → New → Blueprint → connect GitHub and pick `esp32cam-security`
   (or New → Web Service with the same build/start commands).
2. Fill the secrets it asks for:

| variable | value |
|---|---|
| `SUPABASE_URL` | Project URL from step 1 |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role key from step 1 |
| `SETUP_CODE` | any secret phrase; creates the first owner account |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` | `npx web-push generate-vapid-keys` |
| `TELEGRAM_BOT_TOKEN` | optional, from @BotFather |

`JWT_SECRET` and `TELEGRAM_WEBHOOK_SECRET` are generated by Render.

3. Deploy. The app is at `https://<service>.onrender.com`, the API at `…/api`.

Free-plan behaviour: the service sleeps after 15 minutes with **no incoming requests** and takes
~1 minute to wake. The camera's heartbeat and command polling keep it awake while the board is
powered. With the board off, the first app visit is slow, and the OFFLINE timer only runs while
the service is awake.

## 3. Firmware

`firmware/include/secrets.h`:

```c
#define WIFI_SSID            "your hotspot"
#define WIFI_PASSWORD        "..."
#define DEVICE_ID            "cam-01"
#define DEVICE_UPLOAD_KEY    "same key you register in the app"
#define AZURE_IOT_HUB_HOST   ""
#define USE_LOCAL_DEV_SERVER 1                                      // HTTPS device link
#define API_BASE_URL         "https://<service>.onrender.com/api"
```

HTTPS certificates are checked against the root bundle built into the ESP32 core.

## 4. First use

Open the Render URL on your phone → *First setup* with your `SETUP_CODE` → *Family → Devices* →
register `cam-01` with the upload key → power the board. Status turns from OFFLINE to DISARMED
within a minute.

## Differences to know for the viva

- Supabase signed **upload** URLs live 2 hours (fixed by Supabase) instead of 5 minutes. Each is
  still bound to one server-chosen object path and cannot overwrite it.
- Commands arrive within ~3 s (the poll interval) instead of being pushed instantly over MQTT.
- The device authenticates every request with its upload key over TLS instead of an IoT Hub SAS token.
